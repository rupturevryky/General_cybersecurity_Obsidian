# Чтение и диагностика HTTP

HTTP-транзакция состоит из запроса клиента и ответа сервера. Для работы в ИБ важно уметь восстановить: куда отправлен запрос, каким методом, с какими заголовками и телом, какой компонент ответил и где возникла ошибка.

## Запрос

```http
POST /api/session HTTP/1.1
Host: example.test
Content-Type: application/json
Accept: application/json
Cookie: session=...

{"username":"alice","password":"..."}
```

Стартовая строка содержит метод, target и версию протокола. `Host` выбирает виртуальный хост. `Content-Type` описывает формат тела, а `Accept` — предпочтительный формат ответа. Заголовок не следует считать истинным без проверки фактического содержимого.

## Ответ

```http
HTTP/1.1 200 OK
Content-Type: application/json
Set-Cookie: session=...; Secure; HttpOnly; SameSite=Lax
Cache-Control: no-store

{"authenticated":true}
```

Код состояния описывает результат обработки на HTTP-уровне, но не бизнес-успех. Приложение может вернуть `200` с сообщением об ошибке. Redirect требует анализа `Location`; кэширование — `Cache-Control`, `Age`, `ETag` и промежуточных узлов.

## Диагностический порядок

```bash
curl -v --connect-timeout 5 https://example.test/
curl -I https://example.test/
curl --resolve example.test:443:192.0.2.10 https://example.test/
```

Разделяйте этапы: DNS → TCP → TLS → HTTP → логика приложения. `curl -v` может вывести чувствительные заголовки; перед публикацией удаляйте cookies, токены и персональные данные. `--resolve` временно связывает имя и адрес для одного вызова, сохраняя корректные Host и SNI.

## HTTP/1.1, HTTP/2 и HTTP/3

HTTP/2 мультиплексирует потоки в одном TCP-соединении и сжимает заголовки. HTTP/3 переносит HTTP поверх QUIC/UDP. Семантика методов и кодов в основном сохраняется, но сетевое поведение и формат трассировки различаются. Не путайте версию HTTP с наличием TLS: на практике браузерный HTTP/2 и HTTP/3 обычно защищены TLS.
