## Клиент, сервер и ресурс

Клиент отправляет запрос, сервер возвращает ответ. Браузер — клиент, но HTTP используют также мобильные приложения, API-клиенты и другие серверы. Ресурсом может быть HTML, изображение, JSON, файл или результат вычисления.

HTTP — прикладной протокол поверх сетевого транспорта. HTTPS означает HTTP внутри защищённого TLS-соединения.

## Из чего состоит URL

```text
https://example.org:8443/catalog/item?id=42#details
```

| Часть | Пример | Назначение |
| --- | --- | --- |
| схема | `https` | правила обращения |
| host | `example.org` | имя узла, разрешаемое через DNS |
| port | `8443` | транспортный порт |
| path | `/catalog/item` | путь ресурса |
| query | `id=42` | параметры запроса |
| fragment | `details` | обрабатывается клиентом и обычно не отправляется серверу |

Несколько сайтов могут обслуживаться одним IP-адресом.

## Путь запроса

1. Браузер разбирает URL и проверяет кэш.
2. DNS возвращает IP-адрес.
3. ОС выбирает маршрут и устанавливает транспортное соединение.
4. Для HTTPS клиент проверяет сертификат и согласует TLS.
5. Клиент отправляет HTTP-запрос.
6. Reverse proxy или веб-сервер выбирает виртуальный host и передаёт запрос приложению.
7. Приложение формирует ответ.
8. Браузер применяет политики, cookies и кэш и отображает содержимое.

## Запрос и ответ

```http
GET /profile?id=42 HTTP/1.1
Host: example.org
Accept: text/html
Cookie: session=opaque-value

```

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1250
Cache-Control: no-store

<html>...</html>
```

После стартовой строки идут заголовки, пустая строка и необязательное тело. HTTP/2 и HTTP/3 иначе кодируют данные на линии, но сохраняют семантику методов, статусов и заголовков.

## Методы

- `GET` получает представление и не должен менять состояние.
- `HEAD` получает только соответствующие заголовки.
- `POST` передаёт данные для обработки.
- `PUT` обычно создаёт или заменяет ресурс по известному URI.
- `PATCH` частично изменяет ресурс.
- `DELETE` запрашивает удаление.
- `OPTIONS` сообщает возможности и участвует в CORS preflight.

Это договорённости, а не защита. Сервер отдельно проверяет аутентификацию, полномочия и данные.

## Коды состояния

| Класс | Смысл | Примеры |
| --- | --- | --- |
| `1xx` | промежуточная информация | `101` |
| `2xx` | запрос обработан | `200`, `201`, `204` |
| `3xx` | перенаправление или кэш | `301`, `302`, `304` |
| `4xx` | проблема запроса или доступа | `400`, `401`, `403`, `404`, `429` |
| `5xx` | ошибка обработки сервером | `500`, `502`, `503`, `504` |

`401` обычно означает отсутствие приемлемой аутентификации, `403` — отказ запросу. `404` иногда намеренно скрывает существование ресурса.

## Заголовки, cookies и состояние

`Host` выбирает сайт, `Content-Type` описывает тело, `Authorization` передаёт учётные данные, `Location` задаёт перенаправление, `Cache-Control` управляет кэшем.

HTTP сам по себе не хранит сеанс между запросами. Сервер отправляет `Set-Cookie`, после чего браузер прикладывает cookie к подходящим запросам. Важные атрибуты:

- `Secure` — только HTTPS;
- `HttpOnly` — запрет обычного чтения из JavaScript;
- `SameSite` — ограничение межсайтовой отправки;
- `Domain` и `Path` — область;
- `Expires` или `Max-Age` — срок жизни.

## TLS и сертификат

TLS обеспечивает шифрование канала, целостность и проверку имени сервера. Сертификат связывает открытый ключ с именами и цепочкой доверия. Проверяются имя, срок действия и доверенный центр сертификации.

HTTPS не устраняет ошибки приложения: SQL injection или слабая авторизация остаются возможны. TLS защищает передачу, а не бизнес-логику.

## Origin и границы браузера

Origin образуют схема, host и порт. Изменение любого компонента создаёт другой origin. Same-origin policy ограничивает чтение данных между origin, а CORS контролируемо ослабляет часть ограничений.

Подробнее: [[Учебный курс — кибербезопасность/04 Безопасность приложений/02 Web-платформа/02 Same-origin policy и CORS|Same-origin policy и CORS]].

## Веб-сервер и reverse proxy

Apache и Nginx принимают соединения, выбирают виртуальный host, обслуживают файлы, завершают TLS и передают динамический запрос приложению. Reverse proxy не исправляет автоматически ошибки авторизации и валидации.
