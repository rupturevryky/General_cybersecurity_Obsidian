# TLS, reverse proxy и границы доверия

TLS обеспечивает конфиденциальность и целостность канала и подтверждает, что сторона владеет ключом, соответствующим проверенному сертификату. Он не доказывает безопасность приложения и не защищает данные после расшифрования на конечном узле.

## Сертификат и имя

Клиент проверяет цепочку доверия, срок действия и соответствие имени полям Subject Alternative Name. SNI сообщает серверу имя ещё при установлении TLS, чтобы тот выбрал сертификат. Ошибка сертификата может означать неверное имя, время, цепочку, перехватывающий proxy или неправильную конфигурацию.

```bash
openssl s_client -connect example.test:443 -servername example.test </dev/null
curl -v https://example.test/
```

Не используйте отключение проверки сертификата как исправление. Сначала установите, какая именно проверка не прошла.

## Reverse proxy

Reverse proxy принимает клиентское соединение и передаёт запрос backend-приложению. На нём могут завершаться TLS, аутентификация, rate limiting и маршрутизация. Поэтому появляется граница доверия: backend не должен безусловно доверять `X-Forwarded-For`, `X-Forwarded-Proto` и `Host` от произвольного клиента. Доверенные proxy и правила перезаписи должны быть заданы явно.

```text
клиент → CDN/WAF → reverse proxy → приложение → база данных
```

В журналах каждого звена могут быть разные адреса, request ID и часы. Для расследования заранее определяют единый correlation ID, синхронизацию времени и политику очистки чувствительных полей.

## Forward proxy и VPN

Forward proxy действует от имени клиента к внешним ресурсам; reverse proxy — от имени сервиса перед backend. VPN создаёт защищённый сетевой путь, но не заменяет аутентификацию и авторизацию приложений.
