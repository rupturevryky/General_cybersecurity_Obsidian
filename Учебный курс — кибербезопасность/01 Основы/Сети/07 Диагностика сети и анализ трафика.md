# Диагностика сети и анализ трафика

Сетевая диагностика должна отвечать на конкретный вопрос, а не начинаться со случайного набора команд. Полезная модель: имя → адрес → маршрут → транспортное соединение → TLS → прикладной протокол.

## Базовый порядок

1. определить источник, назначение, время и ожидаемый сервис;
2. проверить DNS и используемый адрес;
3. проверить локальный адрес, маршрут и шлюз;
4. установить, слушает ли сервер нужный сокет;
5. проверить TCP/UDP и фильтрацию;
6. проверить прикладной ответ и журналы обеих сторон.

```bash
dig example.test A AAAA
ip route get 192.0.2.10
ss -lntup
traceroute 192.0.2.10
curl -v --connect-timeout 5 https://example.test/
```

В Windows соответствующие средства: `Resolve-DnsName`, `Get-NetRoute`, `Test-NetConnection` и `Get-NetTCPConnection`.

## Захват пакетов

Фильтр захвата ограничивает собираемые пакеты, display filter — уже захваченные. Минимизируйте объём: дамп может содержать токены, персональные данные и внутреннюю топологию.

```bash
sudo tcpdump -ni any 'host 192.0.2.10 and tcp port 443'
```

SYN без ответа указывает на потерю или фильтрацию после точки захвата; RST обычно означает достижимый узел без принимающего сокета или явный reject; завершённый handshake без ответа приложения переносит проверку выше транспортного уровня. Это гипотезы, которые подтверждают наблюдением с другой стороны.

## Частые ошибки

- считать успешный `ping` доказательством доступности приложения;
- считать неуспешный `ping` доказательством недоступности узла;
- игнорировать IPv6, split DNS, proxy и NAT;
- путать адрес, видимый клиенту, с адресом backend;
- публиковать pcap без очистки и разрешения.
