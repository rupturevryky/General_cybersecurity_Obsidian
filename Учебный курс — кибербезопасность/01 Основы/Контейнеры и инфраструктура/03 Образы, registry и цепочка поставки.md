# Образы, registry и цепочка поставки

Контейнерный образ состоит из неизменяемых слоёв и метаданных. Tag — изменяемое имя, digest — идентификатор конкретного содержимого. Для воспроизводимости и контроля поставки важнее digest, но он не доказывает безопасность образа.

## Цепочка доверия

```text
исходный код → зависимости → сборка → образ → registry → deployment → runtime
```

На каждом этапе нужны происхождение, контроль изменений и минимальные права. Уязвимость может прийти из базового образа, пакета, build script, CI-секрета или подменённого registry.

## Практичный baseline Dockerfile

- использовать поддерживаемый минимальный базовый образ из доверенного источника;
- фиксировать зависимости осознанно и регулярно обновлять;
- не помещать секреты в `ARG`, `ENV`, `COPY` и слои;
- выполнять приложение непривилегированным пользователем;
- копировать только нужные файлы через `.dockerignore`;
- не устанавливать лишние отладочные и сетевые инструменты;
- задавать исполняемый файл предсказуемой exec-формой;
- сканировать образ, но проверять применимость результата вручную.

Multi-stage build отделяет среду сборки от runtime и уменьшает образ. SBOM перечисляет компоненты, а подпись/attestation связывает артефакт с субъектом и процессом сборки; это разные доказательства.

## Проверка

```bash
docker image inspect image:tag
docker history --no-trunc image:tag
docker image ls --digests
```

История может раскрыть ошибочно добавленные секреты даже после удаления в следующем слое. Скомпрометированный секрет нужно отозвать, а не просто удалить из Dockerfile.

## Внешняя практика

В контейнерной лаборатории внешнего сервиса исследуйте предоставленный образ: происхождение, пользователь, слои, лишние файлы и потенциальные секреты. Не публикуйте образ и найденные данные вне платформы.
