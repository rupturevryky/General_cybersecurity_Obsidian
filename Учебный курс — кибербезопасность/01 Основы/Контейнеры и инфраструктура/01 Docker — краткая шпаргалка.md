# Docker: модель и базовые команды

> [!abstract] Цель
> Понять разницу между образом и контейнером, роль Dockerfile, registry, сети и хранилища, а затем использовать команды осознанно.

## Зачем нужны контейнеры

Контейнер упаковывает приложение и его пользовательское окружение и запускает процесс с изоляцией средствами ядра. Контейнеры одного хоста разделяют ядро ОС; этим они отличаются от виртуальных машин, каждая из которых обычно имеет собственное гостевое ядро.

Контейнер не является «лёгкой виртуальной машиной» во всех смыслах. Его главная сущность — один или несколько изолированных процессов. Остановка главного процесса обычно завершает контейнер.

## Основные сущности

| Сущность | Значение |
| --- | --- |
| Dockerfile | рецепт сборки образа |
| image | неизменяемый шаблон из слоёв |
| container | запущенный или остановленный экземпляр образа с изменяемым слоем |
| registry | хранилище образов, например Docker Hub или внутренний registry |
| volume | управляемое Docker постоянное хранилище |
| bind mount | подключение выбранного пути хоста внутрь контейнера |
| network | виртуальная сеть и правила взаимодействия контейнеров |

Удаление контейнера обычно удаляет его изменяемый слой, поэтому важные данные выносят в volume, внешнюю БД или другое предусмотренное хранилище.

## Получение и проверка образа

```bash
docker pull nginx:1.27
docker image ls
docker image inspect nginx:1.27
```

Тег — изменяемая метка, а digest однозначно указывает содержимое. В воспроизводимой и чувствительной среде фиксируют версию или digest и контролируют происхождение образа.

## Запуск контейнера

```bash
docker run --name web -d -p 127.0.0.1:8080:80 nginx:1.27
```

- `--name web` задаёт удобное имя;
- `-d` запускает в фоне;
- `-p 127.0.0.1:8080:80` публикует порт контейнера `80` только на loopback хоста `8080`;
- последний аргумент задаёт образ.

Запись `-p 8080:80` без адреса обычно публикует порт на всех подходящих интерфейсах хоста. Это может неожиданно открыть сервис сети.

```bash
docker ps
docker ps -a
docker logs web
docker inspect web
docker stop web
docker start web
docker rm web
```

## Выполнение команды внутри

```bash
docker exec -it web sh
```

`exec` запускает дополнительный процесс в уже работающем контейнере. Наличие `bash` не гарантируется; минимальный образ может содержать только `sh` или не содержать оболочку вообще. Ручное изменение работающего контейнера плохо воспроизводится — постоянные изменения вносят в Dockerfile и пересобирают образ.

## Сборка образа

```dockerfile
FROM nginx:1.27
COPY ./site/ /usr/share/nginx/html/
USER nginx
```

```bash
docker build -t training-web:1.0 .
```

Контекст сборки — каталог, переданный последним аргументом. Файл `.dockerignore` исключает ненужные и чувствительные данные. Секреты нельзя помещать через `COPY` или обычный `ARG`: они могут остаться в контексте или слоях.

## Данные

```bash
docker volume create app-data
docker run --mount type=volume,src=app-data,dst=/var/lib/app image
docker run --mount type=bind,src=/srv/config,dst=/etc/app,readonly image
```

Bind mount даёт контейнеру доступ к пути хоста. Ошибка в пути или режиме записи способна повредить данные хоста. Volume меньше зависит от структуры каталогов хоста и управляется Docker.

## Сеть и имена

В пользовательской Docker-сети контейнеры обычно обращаются друг к другу по имени контейнера или Compose-сервиса. `localhost` внутри контейнера означает сам контейнер, а не хост и не соседний контейнер.

```bash
docker network create app-net
docker run -d --name db --network app-net postgres
docker run -d --name app --network app-net application
```

Публикация порта нужна для доступа извне Docker-сети, но не для обычного общения контейнеров в одной сети.

## Граница безопасности

Docker daemon обладает широкими правами на хосте. Пользователь с доступом к Docker socket часто способен получить эквивалент административного контроля. Поэтому:

- не подключайте `/var/run/docker.sock` без строгой необходимости;
- не запускайте `--privileged` как универсальное решение;
- ограничивайте capabilities и файловую систему;
- запускайте приложение не от root, если это возможно;
- сканируйте зависимости и обновляйте базовые образы;
- не храните секреты в образе и переменных, доступных всем процессам;
- различайте уязвимость образа, контейнера, daemon и хоста.

## Диагностический порядок

1. `docker ps -a` — создан ли контейнер и как завершился.
2. `docker logs` — что сообщил главный процесс.
3. `docker inspect` — команда, mounts, сеть и публикация портов.
4. Проверить свободное место и состояние daemon.
5. Проверить доступ по адресу хоста, а затем из нужной сети.
