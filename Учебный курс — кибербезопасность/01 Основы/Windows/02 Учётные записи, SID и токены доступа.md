# Учётные записи, SID и токены доступа

> [!abstract] Результат
> Ученик объясняет разницу между идентификацией, аутентификацией и авторизацией, читает SID и группы в token, различает локальный и доменный контекст.

## Три разных вопроса

- **Идентификация**: кем субъект представляется.
- **Аутентификация**: как система проверяет заявление.
- **Авторизация**: какие действия разрешены после проверки.

Пароль участвует в аутентификации, но сам по себе не описывает права. Права выводятся из SID пользователя, групп, privileges, token и политики объекта.

## Локальные и доменные учётные записи

Локальная учётная запись хранится и управляется конкретным компьютером. Доменная — централизованной службой каталога и может использоваться на разных устройствах. Одинаковое отображаемое имя не означает одну идентичность.

```text
WORKSTATION\alice
DOMAIN\alice
alice@example.org
```

На отдельной машине сведения локальных учётных записей связаны с SAM. В доменной среде идентичности и политика относятся к Active Directory. Подробное устройство AD изучается в профильном разделе курса.

## SID и RID

Security Identifier — уникальный идентификатор security principal. Пример:

```text
S-1-5-21-111111111-222222222-333333333-1001
```

Последняя часть часто является RID, различающим объекты внутри authority или домена. Переименование пользователя не меняет его SID. Удаление и создание пользователя с тем же именем обычно создаёт новый SID, поэтому старые ACL могут показать неизвестный SID.

Well-known SID описывают встроенные контексты и группы. Нельзя выдавать права, ориентируясь только на локализованное отображаемое имя.

## Группы

Группы упрощают назначение доступа. Пользователь может иметь основную и вложенные группы, а членство способно приходить из локальной и доменной областей. При входе значимые SID групп попадают в token.

Особенно чувствительны Administrators, Remote Desktop Users, Backup Operators и группы, которым делегированы права служб или приложений. Название группы не раскрывает всех возможностей: нужно исследовать фактические разрешения и privileges.

## Access token

Каждый процесс имеет primary access token, описывающий его security context. Token включает SID пользователя, группы, privileges, logon SID, integrity level, тип token и другие атрибуты. Поток может временно использовать impersonation token клиента.

Когда поток открывает защищаемый объект, Windows сравнивает token с security descriptor объекта. Token — не пароль и не файл с секретом; это объект ядра, представляющий уже установленный контекст.

**Primary token** задаёт основной контекст процесса. **Impersonation token** позволяет серверному потоку выполнять проверяемую операцию в контексте клиента. Impersonation полезен, но ошибки конфигурации привилегий и служб могут создавать путь повышения прав.

## Privileges и permissions

Permission относится к конкретному объекту: например, право прочитать файл. Privilege разрешает системную операцию: отладку процессов, резервное копирование или impersonation. Privilege присутствует в token и может быть включён или выключен.

Примеры чувствительных privileges:

- `SeDebugPrivilege`;
- `SeBackupPrivilege` и `SeRestorePrivilege`;
- `SeImpersonatePrivilege`;
- `SeTakeOwnershipPrivilege`;
- `SeLoadDriverPrivilege`.

Наличие privilege не означает, что он обязательно включён или уже использован.

## Служебные идентичности

- `LocalSystem` имеет очень высокие локальные полномочия и при сетевом доступе часто представляет учётную запись компьютера.
- `LocalService` имеет ограниченные локальные права и обычно анонимный сетевой контекст.
- `NetworkService` имеет ограниченные локальные права и может представлять компьютер в сети.
- Виртуальные и управляемые service accounts уменьшают необходимость ручного управления паролями.

## Проверка

```powershell
whoami /user
whoami /groups
whoami /priv
Get-LocalUser
Get-LocalGroup
Get-LocalGroupMember Administrators
```

## Ошибочные утверждения

- «Имя пользователя уникально» — уникальность обеспечивает SID в своей области.
- «Член Administrators всегда работает с полными правами» — UAC обычно использует отфильтрованный token до elevation.
- «Disabled privilege отсутствует» — он может присутствовать в token, но быть выключен.
- «SYSTEM и Administrator одно и то же» — это разные security contexts.
