# NTFS, ACL и привилегии

> [!abstract] Результат
> Ученик читает security descriptor, различает DACL и SACL, объясняет наследование и effective access, не путает права NTFS, share permissions и privileges.

## Защищаемые объекты

Windows применяет общую модель доступа к файлам, каталогам, ключам реестра, процессам, службам, именованным каналам и другим securable objects. С объектом связан **security descriptor**.

Основные компоненты:

- SID владельца;
- SID primary group;
- DACL;
- SACL;
- управляющие флаги, включая наследование.

## ACE, DACL и SACL

ACL состоит из Access Control Entries. ACE указывает trustee — пользователя или группу — и набор разрешаемых, запрещаемых или аудируемых действий.

**DACL** определяет, кому доступ разрешён или запрещён. **SACL** определяет, какие попытки доступа должны создавать аудит. SACL не предоставляет доступ.

Важная тонкость: отсутствие DACL и пустая DACL — не одно и то же. Null DACL допускает полный доступ, пустая DACL не содержит разрешающих ACE и потому никому его не предоставляет.

## Владелец

Владелец управляет частью security descriptor и обычно может изменить DACL. Возможность стать владельцем чувствительна: она способна косвенно привести к получению доступа даже без исходного Allow ACE.

## Наследование

Дочерний объект может наследовать ACE от каталога. ACE бывают явными и наследуемыми. Отключение наследования может скопировать правила как явные или удалить наследуемые записи — это разные последствия.

Для каталогов права имеют отдельную семантику: просмотр имён, создание файлов, создание подкаталогов, удаление дочерних объектов и traversal. Разрешение на файл не всегда помогает, если нет возможности пройти родительский путь.

## Allow, Deny и effective access

Результат зависит от token пользователя, групп, типа запрошенного доступа и порядка ACE. Явный Deny часто применяется для специальных исключений, но чрезмерное использование усложняет анализ. Лучше выдавать минимальные Allow группам с понятной ролью.

Effective access — итог для конкретного субъекта и операции. Его нельзя надёжно определить по одной строке ACL без учёта token, наследования, владельца, privileges и типа объекта.

## NTFS и SMB

При доступе к `\\server\share\file` применяются разрешения общего ресурса SMB и NTFS. Итог ограничивается обоими уровнями. При локальном доступе к тому же файлу share permissions не участвуют.

Это частый вопрос собеседования: широкое разрешение на share не отменяет строгую DACL NTFS, и наоборот.

## SDDL

Security Descriptor Definition Language — компактное текстовое представление. Компоненты начинаются с `O:` для owner, `G:` для group, `D:` для DACL и `S:` для SACL. Для начального уровня достаточно узнавать структуру; ручное редактирование без проверки рискованно.

## Команды чтения

```powershell
Get-Acl C:\Path | Format-List
(Get-Acl C:\Path).Access
icacls C:\Path
Get-SmbShareAccess -Name ShareName
```

Перед изменением сохраните исходный descriptor:

```powershell
Get-Acl C:\Path | Export-Clixml .\acl-backup.xml
```

В учебном курсе изменяющие ACL-команды выполняются только по заданию внешней платформы.

## Типичные риски

- обычный пользователь может изменить исполняемый файл службы;
- каталог приложения допускает создание DLL или конфигурации;
- share раскрывает данные более широкой группе;
- наследование случайно распространяет чувствительное разрешение;
- SACL не настроена, и важный доступ не журналируется;
- владелец или группа имеют неожиданные SID.

## Рабочий сценарий

На внешней платформе пользователь может заменить конфигурацию службы, но не её EXE. Объясните, почему это всё равно может быть критично и какие процессы, ACL и журналы нужно исследовать.
