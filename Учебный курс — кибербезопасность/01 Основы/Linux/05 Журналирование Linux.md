# Журналирование Linux

> [!abstract] Цель
> Понимать, какие события записывает система, где искать причину сбоя и как собрать данные, не уничтожив важный контекст.

## Событие, журнал и источник

Журнал — последовательность записей о событиях. Запись обычно содержит время, имя узла, источник, уровень важности, идентификатор процесса и сообщение. Журнал не является абсолютной истиной: приложение может ничего не записать, часы могут быть неверны, а злоумышленник с высокими правами способен изменить локальные данные.

Источники событий:

- ядро;
- менеджер служб и системные сервисы;
- механизм аутентификации и `sudo`;
- сетевые службы, например SSH и веб-сервер;
- прикладные программы;
- средства аудита и защиты.

Перед расследованием уточняют часовой пояс, синхронизацию времени, имя узла и период события. Без этого записи разных систем трудно сопоставить.

## systemd-journald и journalctl

Во многих современных дистрибутивах `systemd-journald` собирает структурированные события. Команда `journalctl` читает журнал:

```bash
journalctl                     # все доступные события
journalctl -b                  # текущая загрузка системы
journalctl -b -1               # предыдущая загрузка
journalctl -u ssh --since today
journalctl -p warning..alert   # предупреждения и более важные события
journalctl -k                  # сообщения ядра
journalctl -f                  # следить за новыми записями
journalctl --since "2026-08-24 10:00" --until "2026-08-24 10:15"
```

Имя unit нужно брать из `systemctl status`, например `ssh.service` или `sshd.service`. Для диагностики сначала ограничьте время и источник, затем расширяйте область.

`journalctl -o json-pretty` показывает структурированные поля. Полезны `_SYSTEMD_UNIT`, `_PID`, `_UID`, `SYSLOG_IDENTIFIER` и `_BOOT_ID`.

## Текстовые журналы в /var/log

Конкретные файлы зависят от дистрибутива и настройки syslog:

| Путь | Типичное содержимое |
| --- | --- |
| `/var/log/auth.log` | аутентификация и `sudo` в Debian/Ubuntu |
| `/var/log/secure` | аналогичные события в RHEL-подобных системах |
| `/var/log/syslog` | общесистемные сообщения Debian/Ubuntu |
| `/var/log/messages` | общесистемные сообщения ряда других систем |
| `/var/log/kern.log` | сообщения ядра, если настроен отдельный файл |
| `/var/log/nginx/`, `/var/log/apache2/` | журналы веб-серверов |

Не следует предполагать, что каждая команда `sudo` обязательно находится только в `/var/log/auth.log`: событие может храниться в journal, другом файле или удалённой системе.

Безопасный поиск:

```bash
sudo less /var/log/auth.log
sudo grep -i "failed" /var/log/auth.log
sudo zgrep -i "failed" /var/log/auth.log.*.gz
```

## Syslog и уровни важности

Syslog описывает передачу сообщений с facility и severity. Уровни от наиболее критичного к отладочному: `emerg`, `alert`, `crit`, `err`, `warning`, `notice`, `info`, `debug`. Уровень назначает разработчик, поэтому важное событие иногда оказывается `info`, а повторяющаяся ошибка может быть симптомом, но не первопричиной.

Реализации `rsyslog` и `syslog-ng` могут фильтровать сообщения, писать их в файлы и пересылать на центральный сервер. Удалённое хранение уменьшает риск потери журналов при отказе или компрометации одного узла.

## Ротация и срок хранения

Журналы растут и занимают диск. `logrotate` переименовывает, сжимает и удаляет старые файлы по правилам. Настройки обычно находятся в `/etc/logrotate.conf` и `/etc/logrotate.d/`. Journal ограничивается параметрами `journald.conf` и доступным дисковым пространством.

```bash
journalctl --disk-usage
systemctl status logrotate.timer
```

Ротация означает, что поиск только в текущем файле может пропустить событие. Политика хранения должна учитывать требования расследования и защиты персональных данных.

## Базовый алгоритм диагностики

1. Зафиксировать симптом и точное время с часовым поясом.
2. Проверить состояние службы: `systemctl status имя`.
3. Посмотреть события unit за узкий период.
4. Проверить сообщения ядра, аутентификацию и журнал приложения.
5. Сопоставить PID, пользователя, адрес источника и идентификатор запроса.
6. Сохранить исходные записи и описать применённые фильтры.
7. Только после сбора данных перезапускать службу или очищать состояние.

## Ограничения безопасности

- Не публикуйте журналы без проверки: они содержат адреса, имена, токены и другие секреты.
- Не используйте `rm` или очистку journal как способ «починить» заполненный диск до сохранения доказательств.
- Проверяйте права на журналы и конфигурацию пересылки.
- Отсутствие записи не доказывает отсутствие события.
